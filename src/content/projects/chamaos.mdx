<Callout variant="note" title="Where this project actually stands">
This is a **working prototype that runs in development on my own machine** — Expo on an
emulator and a physical device. It has no users, is not on any store or test track, and has
never held a real group's money. The offline synchronisation model described below is
**designed and specified, not built**: the app currently writes online only. I have kept the
design section because the reasoning is the point of the project, but nothing here should be
read as a shipped system.
</Callout>

## The problem

A chama is a rotating savings group. Members contribute a fixed amount on a fixed schedule and
the pot goes to one member per cycle. In Kenya this is not a niche activity — it is how a very
large amount of household capital actually moves.

The bookkeeping is usually a notebook, a WhatsApp group, and a treasurer's memory. That works
until it does not, and when it fails it fails as a dispute about money between people who know
each other and have to keep knowing each other afterwards.

So the software problem is small and the trust problem is the whole thing. A ledger that any
member could plausibly have edited is worth less than the notebook it replaced, because the
notebook at least has one obvious custodian.

## The design question

Almost every decision in this prototype comes from one question: *when a member looks at a
number on their phone, why should any other member believe it?*

That rules out the obvious implementation immediately. If the device sums the contributions it
knows about, then two members with different sync states see different totals, and the app has
manufactured exactly the dispute it was supposed to prevent.

<Callout variant="decision" title="Decision: totals are server-computed, always">
Balances and contribution totals are written by a Cloud Function triggered on contribution
writes, never summed on the device. The client displays a number it was given; it has no code
path that produces one.

The cost is latency — a total can lag its contribution by a second or two, and the UI has to
show that honestly rather than papering over it. The benefit is that no member can be shown a
figure another member's phone disagrees with, which is the entire product.
</Callout>

### Permissions where they cannot be bypassed

Members can create their own contributions. Treasurers can confirm anyone's. Chairs can alter
group membership.

None of that is expressed as a hidden button, because a hidden button is a suggestion. It is
expressed in Firestore security rules, which run on Google's side of the trust boundary and
apply identically to the app, to a rooted device, and to `curl`. The UI hides the controls too —
but only as a courtesy, and never as the mechanism.

This is the part of the prototype I am most confident is correct, because it is the part where
being wrong is testable: I can attempt the write directly and watch it be refused.

## What is designed but not built

<Callout variant="warning" title="Offline sync: specified, not implemented">
The app currently requires connectivity to write. The intended model is:

- **Client-generated deterministic ids**, so a contribution retried after a dropped network
  carries the same id and the server write is an idempotent upsert rather than a second record.
  Letting the backend assign ids means a lost response is indistinguishable from a failed
  write, and the client's only options are to risk a duplicate or risk losing the entry.
- **Honest pending state** — an unsynced contribution renders immediately, visibly pending,
  and is never styled as confirmed until the server says so. Optimistic UI that lies is worse
  than a spinner in an app about money, because people make decisions from what the screen says.

Neither is written yet. On the connections this app would actually be used on, the case they
handle is not rare, which is why they are the next thing rather than a nice-to-have.
</Callout>

## Trade-offs

<Callout variant="warning" title="Firestore was probably the wrong database">
A chama's data is aggressively relational: groups have members, members have contributions,
cycles have payouts, and almost every useful question is a join. Firestore gave me offline
persistence, realtime listeners and security rules for free — which is why I chose it — and
then charged me for it in denormalised writes that have to be kept consistent by hand inside
Cloud Functions.

Postgres with a sync layer would have been more work upfront and less work now. I would still
have picked Firestore to reach a working prototype this fast, but I would not defend it as the
long-term choice, and I would rather say that here than be asked about it in an interview.
</Callout>

## What I would do differently

Model the ledger as append-only from the start. A contribution should never be edited — a
correction should be a second entry that references the first and is attributable to whoever
made it.

That is how the paper notebook already works, and it dissolves the offline merge problem above
rather than solving it: appended entries never conflict with each other, they only need
ordering. I designed a mutable record because it was the obvious shape, and every hard question
since has come from that one choice.
